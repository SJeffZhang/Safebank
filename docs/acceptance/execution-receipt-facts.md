## 输入、输出与边界

输入：当前 AgentState 的 `session_id`、`plan_id`、`plan_draft`、`decision`、`execution`，以及已经读取的展示标签。
输出：按同一计划/步骤和实际执行状态生成的确定性回执。关键事实缺失时提示查看记录核对，不从余额、限额、用户原话或自由文本猜交易金额。
依赖：现有 contracts 与 L1 respond/verify；不新增依赖、不改 L2/L3，不触发读取或再次执行。
失败条件：错金额透传，计划/步骤/目标互换，失败或未结算订单宣称到账，修复失败透传，重新执行交易。

## 根因与修改

- 原成功摘要调用模型，输出校验只检查金额是否存在于混合数字集合，不能区分交易、余额与限额。`10000` 分转账和 `590000` 分余额同时读取 `500000` 分限额时，模型的“转账5000元”能通过。
- 新私有模块 `execution_receipts.py` 由 respond 和 verify 共用；成功路径不调用模型或模型修复。verify 会重新生成回执，任意 `reply_draft` 无法覆盖实际事实。
- 严格要求当前 session、state/decision/execution 的同一 plan_id、完整有效 PlanDraft/ExecutionResult、实际提交时刻、无错误码、完整不重复步骤集合、逐个 step_id/tool/EXECUTED 状态。任一不满足则整份保守兜底，不宣称完整成功。
- TransferResult 不回显金额，因此金额只取上述同一执行步骤匹配的已验证 PlanDraft 参数；执行后可用余额只取该步骤实际 result 的 `from_available_after_cents`。不引入或更改授权逻辑。
- 展示名称只来自对应读取工具中同一实体 ID 的唯一短标签，放在引号中；银行断言词、数字/控制字符/标记等可疑文本使用泛称。自由 memo、商户文本、内部ID和账号不进入回执。尾号仅取同一卡 ID 或补卡实际结果，最终保留原有长数字掩码。
- 14种写动作均用同一绑定机制：定时转账单次金额与30日承诺分开；AA区分总额/已收/待收；卡片更新读取实际结果；重复添加/取消/卡状态保留 no_op；订阅节省不说成交易；基金区分待确认、待结算、已结算和未完成，金额/份额绑定订单账户、产品与类型。
- 其他只读输出继续走原数字校验/卡尾号清理/掩码。修复文本额外重跑语义检查；错误、空或仍不合格的修复不能透传已知错误，使用固定模板。保留实际provider调用路径的402/403/429立即中止且仅请求一次负控。
