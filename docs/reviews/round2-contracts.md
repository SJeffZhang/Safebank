## C01 · P1 · agent 自修分支无法补执行缺失的读取

**位置**：§6.1 行 657、674、685–686；§7.9 行 1019；§9.8 行 1339。

**复现**：计划引用未出现在读取账本的产品或收款人，L2 返回 `ENTITY_UNSEEN(resolver=agent)`。图直接回 `plan`；该节点只绑定 `submit_action_plan`，不能调用 read 工具。虽然规格允许“补读取”，实际没有回到 `gather` 的边，也没有 evaluate 节点自动补读的契约，两次重试仍会是同样的未读实体错误。

**建议**：把自修结果细分为 `requires_read` / `plan_only`，或让所有 agent 自修先回 `gather`。`gather` 必须接收原授权与 findings，仅补读，再进入 plan；共享两次修复预算，不重置授权或扩大金额/目标。登记需要补读的字段/工具，避免模型猜新目标。

## C02 · P1 · 澄清分支缺候选取得、服务端登记与回复发送闭环

**位置**：§6.1 行 641–646、671、684；§6.5 行 788；§7.4 行 921、926；§9.5 行 1247、1263–1266；§9.10 行 1375。

**复现**：新会话输入“给王五转钱”，understand 发现缺金额，在任何 R2 读取前走 clarify→END。此时 cards.py 没有本会话读取的收款人候选，也没有 L2 发放的澄清 action ID。另一方面，授权合并要求 L2 已保存 `pending_clarification`，但 G3 返回的 UtteranceRef 没有该对象，G19 只允许 F 发起且描述为核验既有同会话候选，未定义谁建立 pending 状态、怎样让 L1/UI 得到候选动作。clarify 的追问也绕过 verify_output，而 SSE 唯一的回复事件定义为 verify_output 通过后的回复。按图与接口逐字实现，缺参时无法完整发送带可用选择动作的追问。

**建议**：明确单一闭环，例如 G3 在确定性解析时建立并返回 `clarification={id,parent_utterance_id,missing_fields,candidates,expires_at_wall}`，或让 L1 通过一个严格受限的只读/提案接口请求 L2 创建它；候选必须经 L2 查询/核验并发放 action ID。补充回答必须回传 clarification ID、在 L2 合并完整作用域；F3 应向 L1 提供该合并结果。clarify 统一进入 verify_output（候选卡单独 custom），再发送 reply 并 END。若选择其他流程，也需在 G/F 请求返回、存储表和图中同时锁定。

## C03 · P1 · add_payee 的 no-op 与预先派生的步骤引用冲突

**位置**：§6.2 行 758；§7.2 行 884；§8.3 行 1086；§9.4 行 1225。

**复现**：原账户已有收款人 `pye_existing`；用户再次要求添加同一账号并转账，步骤 s2 使用 `{ref:"s1"}`。L2 按规定在契约后把引用解析成 `derive(plan_id,"s1",kind)`；但 W2 按目标唯一约束返回已有 `pye_existing` 且 no_op。于是 s2 指向派生的新 ID，实际不会创建这个 ID；预演或执行将失败，或两层产生不同引用结果。

**建议**：在快照中先解析每个“创建或复用”步骤的实际结果 ID，再构建步骤引用表；新建才采用派生 ID，no-op 映射已有 ID。将解析表随不可变执行信封传递，L3 在版本检查后验证一致；或者规定此情况明确返回 REPLAN 并改为直接引用已有 payee_id。不能同时保留“无条件预解析派生 ID”和“返回已有 ID”而不定义重绑定。

## C04 · P1 · 网关层 D6 攻击评测只有 evaluate，没有合法 execute 路径

**位置**：§9.5 行 1252；§9.6 行 1296、1300、1307；§9.7 行 1320；§10.3 行 1417–1419。

**复现**：runner 经 D6 提交固定草稿，B1 返回可批准计划。计划强制 `origin=agent`；F8/G8 明确只允许对应 origin 的调用方执行，F 不能直接执行 agent 计划。F4 仅恢复 L1 已存在且正在等待该 approval_id 的中断，但 D6 没有创建该 L1 run/interrupt。D6 本身也仅返回 Decision，没有执行或恢复能力。因此“固定草稿隔离 LLM 波动”的网关层测试无法把获准计划提交到 L3，不能取得 A3 的 B1 三步成功状态证据。

**建议**：锁定受控网关测试驱动协议：在可信 runner 内单独建立 A 客户端，只获该 case/sid 的助手令牌，按真实审批结果调用现有 G8；明确如何合法取得所需 A 服务身份及助手令牌，并与 agent 容器内攻击子进程彻底隔离。另一方案是增加白名单 D 执行入口，内部使用相同 A 执行校验，拒绝跳过有效用户批准。两种方案任选一种写入接口、凭证表、runner 流程，不能赋予 agent F/D 权限。

## C05 · P1 · A4 的授权状态证据没有进入 L3 请求契约

**位置**：§8.5 行 1123、1126；§9.1 行 1154；§10.2 行 1405、1411。

**复现**：§10.2 要求 L2 在执行信封中向 L3 传入 `approval_id/evaluation_id/view_hash/risk/confirmed_at_wall/authorization_epoch` 并保存。`POST /internal/plans/execute` 的完整请求却只有 customer_id、plan_id、plan_hash、steps、expected_versions、clock_version；禁止额外字段的通用约定会拒绝所需授权摘要。L3 无法凭这份请求保存 A4/A1 所需批准证据。事件执行的 grant 证据也未在信封中明确。

**建议**：在内部执行请求中显式增加类型化 `authorization_evidence`，分别定义互动计划和 scheduled_grant 的判别联合；原子存进 operation_events/plan_executions，并明确是否参与请求幂等摘要。客户端响应只暴露必要字段。A4 继续按文中要求与可信 BFF 确认事实核对，不能只信 L2 自述。

## C06 · P1 · R1 可用余额曲线遗漏冻结及释放

**位置**：§8.1 行 1056；§8.2 行 1068；§8.3 行 1085、1103；§9.3 行 1183。

**复现**：李四 10-15 申购非即期产品 11,955 元，日终账面仍 12,000，可用仅 45；当日只有新增 PENDING 流水。R1 承诺返回每日 `balance_cents` 与 `available_cents`，但 §8.3 规定曲线只取“已过账记录”的末值，因此该日可用曲线仍显示 12,000。随后 void/到期释放也会被同样排除，与界面当前可用余额和基金生命周期不一致。

**建议**：每天按账户 sequence 取所有影响账面或可用余额的账本阶段末值，包括 PENDING / POST_PENDING / VOID_PENDING；从其 balance_after/available_after 分别取值，非记账操作不制造曲线变动。消费/收入合计另行过滤，不能将“不计收入”误等同于“不影响可用余额历史”。

## C07 · P2 · “全部字段”返回模型漏掉旁注要求字段

**位置**：§9.1 行 1154；§9.3 行 1179、1185、1192；§9.4 行 1225。

**复现**：R3 的显式 data 模型没有 `totals_scope`，紧接文字却要求返回它；W2 result 模型只有 payee_id/target_fingerprint，随后要求 no_op=true。R10 还要求“返回计算口径”，但没有给字段名及类型。采用禁止额外字段、从本章逐字段生成的模型时，返回旁注字段会验证失败，不返回又违反文字要求。

**建议**：把 `totals_scope:Literal["filtered_all"]`、W2 `no_op:bool` 及 R10 的 `normalization_basis`（定义确定枚举/结构）加入显式模型；同步例子与 OpenAPI。此项只要求将既有行为写成同一份契约，不扩大业务范围。

## C08 · P2 · 周期订阅的月费/年费折算尚无确定整数算法

**位置**：§5.4 行 590；§7.5 行 939；§9.3 行 1191–1192、1212；§9.4 行 1234；§12 行 1491。

**复现**：识别器支持周订阅，R9/R10/W11 返回年费、月费与节省金额，X-2 又把“取消订阅月费”作为新定时转账的真实金额。对每周 100 分，`100*52/12`、按自然年出现次数/12、按 30 天频次等会得到不同结果；规格未定义折算与整数舍入，也未规定合计先舍入还是逐项舍入。种子全是月订阅掩盖了这个接口差异。

**建议**：明确展示用标准折算，例如 MONTHLY 年费=金额×12，WEEKLY 年费=金额×52、月费=年费/12 向下取整到分（或选择另一明确规则）；指定逐项/合计舍入顺序和 no-op=0。X-2 若只允许取消月订阅，应在授权模板与契约中明确拒绝周订阅参与，避免把估算月费直接当确切转账授权。
