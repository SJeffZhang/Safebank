## Scope and conclusions

- **D4 permission boundary:** the existing auth matrix requires D service credentials plus `demo-console` JWT audience and console scope. The handler independently requires caller D/console and DEMO/EVAL settings; production routes are not mounted. Browser payload cannot supply `console_session_id`, `due_at`, arbitrary evidence or extra fields. The console JWT's jti supplies the recorded console identity, and L3 snapshot supplies the simulation instant. The new helper `authorize_event` is not a route and is called only after the existing S1 or new D4 authentication checks.
- **Registration and ownership:** L3 requires an account belonging to the payload customer before registering a job. The shared contract rejects bool/float/string money coercion, wrong kind/card/channel/split-item combinations and unknown fields. A complete immutable payload, hash, due instant and source identity are saved. Jobs with a caller request ID are serialized by transaction-level advisory lock and resolve to one event ID; changed instructions conflict. A retry at a later clock or renewed console session returns the original job and therefore preserves the original time/console evidence.
- **No callback authority widening:** the shared event engine reads the saved event from L3; it does not execute callback-supplied amounts or targets. New flat uppercase jobs and legacy wrapped lowercase jobs resolve through the same pure appliers. Demo evidence binds event ID, event kind and, for registrations carrying it, the saved console identity; legacy jobs without a saved console identity retain the pre-existing scheduler fallback. Payload-hash mismatch, wrong evidence or an event due after the simulation clock fails before effects.
- **Customer/card/channel:** core debit checks the actual account owner, current card ID/account binding, card status, selected channel control, single/daily limits and normal posting rules. Plain external debit retains a distinct transaction kind. The added merchant attribute remains data, not an authorization source. Independent pure controls confirmed wrong customer, other card and disabled channel yield unchanged state/no effects.
- **AA payment amount and atomic persistence:** the event resolves the actual split containing the item on the declared account. The pure applier requires an unpaid item, exact item amount and an account owned by the customer. The event transaction persists ledger effects and updates only that same customer's/account's still-UNPAID item with PAID/time/event identity; rowcount mismatch raises inside the same `database.begin()` transaction, so partial ledger persistence rolls back. The event job row lock plus clock/customer version lock serialize competing executions. The same event replays its terminal execution; another event targeting an already paid item receives a rejection and no second credit.
- **Event identity and terminal truth:** ledger and operation IDs derive from the actual event ID rather than the old `system/event` constant. Different events do not collide. Pure-applier errors are written as BLOCKED/REJECTED with the actual code rather than SUCCESS. Terminal L3 execution rows are replayed without reapplying effects, and the gateway finalizes from the actual L3 result. Unhandled transient failures release the gateway claim rather than orphaning it.
