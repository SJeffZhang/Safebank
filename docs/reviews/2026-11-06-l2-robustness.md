## 1. 总体结论

L2 的**安全判定本身是稳的**：G4（计划评估）、G3 参数校验、S1 内部回调对畸形输入都正确返回 422，没有发现任何畸形输入能让资金或授权被放行。

但「崩溃」是真实存在的，集中在 **5 类输入校验缺口**。它们都表现为：请求抛出未处理异常 → 全局兜底返回 **503 DEPENDENCY_UNAVAILABLE**（伪装成“依赖不可用”）→ L1/前端把它当作服务故障。同时容器日志是空的，出了问题无法定位。

另外，用户感受到的「不 work」有很大一部分不是崩溃，而是 **G3 原话解析过于保守**：稍微换个说法就判为 `INTENT_UNCLEAR`，转成表单追问。

## 2. 崩溃类缺陷（P0，均已复现）

| # | 现象 | 触发输入 | 位置 | 影响 |
|---|---|---|---|---|
| C1 | G8 执行接口请求体校验失败时自身崩溃 | 缺 `request_id`、`request_id` 为数字/null/对象、`{}`、`null`、数组 | `api/execution.py:1190` 引用了不存在的 `Code.INVALID_REQUEST`（AttributeError） | 本应 422，实际 503；**任何不合规的执行请求都会崩** |
| C2 | G8 读请求体不在 try 内 | 非 JSON、空 body、非 UTF-8 字节 | `api/execution.py:1186` `await request.json()` | JSONDecodeError / UnicodeDecodeError → 503 |
| C3 | 文本或 ID 中含 NUL 字符（`\u0000`）直接进数据库 | G3 原话文本、路径参数（审批/计划/审计/hint/通知 ID）、request_id | Postgres 拒绝 `invalid byte sequence`：`sessions.py:328`、`approvals.py:134`、`execution.py:255`、`notify_audit.py:141`、`idempotency.py:45` 等 | 503；至少 6 条路由 |
| C4 | `request_id` 超长 | 长度 > 256 | 契约 `Id` 无长度上限，表列 `String(256)`；`idempotency.py:45` | 503（通知已读、G8 等） |
| C5 | 幂等辅助函数失败后在已中止的事务里做清理 | 任何在 `produce()` 内触发的数据库错误（如 C3） | `idempotency.py` 失败分支的 DELETE | 二次报错「current transaction is aborted」，**掩盖原始错误** |

横切问题：

- **H1 全局兜底一律 503**（`middleware.py` `_unhandled`）：代码缺陷和真实依赖故障无法区分。L1 遇到 503 会按依赖故障停止，用户只看到失败。
- **H2 没有日志**：长期栈 gateway/agent 容器日志为空，未处理异常没有 traceback、没有 trace_id 关联，线上无法诊断。

## 3. 「能跑但不 work」类问题（P1，功能/体验）

G3 解析对以下合理说法全部判为 `INTENT_UNCLEAR`（安全上是正确的 fail-closed，但体验上像坏了）：

- 带表情或标点：`😀给王五转💰800元`
- 一句多笔：`给王五转800元给赵六转900元`、换行分隔两笔
- 带备注：`给王五转800元，备注：…`
- 口语金额：`八百块五毛`
- 取消订阅类：`取消订阅`、`取消所有订阅`（夹具里有代扣授权）
- 尾号定位卡：`冻结卡号尾号0000的卡`

负数、0、超大金额、非法日期（32 号、2 月 30 日、周八）被拒是**正确的**，但目前和“听不懂”走同一条通用追问，用户得不到具体原因。

## 4. 已验证稳健的部分

- G4：负数/零/超大金额、双目标、无目标、自转、重复 step、未知依赖、自依赖、负/倒序 span、重复来源、未知参数名、多余参数，全部 422；错 session 404，错原话 409，同 id 不同体 409。
- 未知来源引用（未知原话 ref、未知 read、未知 hint/action、越界 span）、未知收款人/卡/订阅：返回 200 决策而非崩溃（基线样本为 REPLAN + UNKNOWN_SENSITIVE_ARG）。**这些样本的具体决策值本轮没有逐一记录，需在下一步确认没有任何一条是 ALLOW。**
- S1 内部回调：畸形 JSON、空体、数组、null 全部 422；缺字段/未知类型返回 RETRYING，不执行。
- 鉴权：无凭证、伪造 Bearer 一律 401，未出现越权。

## 5. 修复计划

全部由协调者亲自实现，**不启动任何 DS worker**；涉及网关安全路径的改动用 Claude 只读子代理独立评审；每个修复先写红测再改（旧代码失败、新代码通过）；合并前在精确 head 上跑完整本机 CI（AGENTS §8.5）。

### 阶段 A：消除崩溃（1 个 PR，约半天）

1. G8：请求体解析放进 try，非法 JSON、非 UTF-8、契约不符统一返回 422 `CONTRACT_INVALID`；删掉不存在的错误码。
2. 输入清洗前置：在 gateway 中间件层统一拒绝路径参数和 JSON 字符串中的 NUL 与非法 UTF-8，返回 422。这样不需要逐个路由打补丁。
3. `request_id` 长度：网关侧按表列上限 256 校验，返回 422。冻结契约 v1 不改；如要改契约，另开 ADR。
4. 幂等清理改用 savepoint：`produce` 失败后回滚到 savepoint 再删占位行，保证原始错误原样抛出。
5. 全局兜底：记录带 trace_id 的 traceback，并让 gateway 容器确实输出日志。是否把未处理异常从 503 改为单独的 500 码，需你拍板：这涉及错误码表（PRD §9.8）和 L1 路由。
6. 把两个探针改造成正式回归 `make test-gateway-robustness`，断言「无任何 5xx、无未处理异常」，并加入 CI。

验收：探针零 5xx、零未处理异常；全部现有 gateway 专项通过；本机完整 CI 通过。

### 阶段 B：扩大覆盖面（约半天）

1. 对 14 个写工具按契约生成边界参数（空、超长、错类型、跨客户 ID），逐条断言决策不是 ALLOW。
2. 补记第 4 节中返回 200 的各样本的决策值，确认全部为 DENY 或 REPLAN。
3. S1：用合法格式但内容伪造的事件（他人客户、过期授权、金额不符），断言 BLOCKED 且 L3 无写入。
4. 检查 BFF 与 L1 对 422/503 的处理，确保显示可读提示而不是整页报错。

### 阶段 C：解析覆盖（P1，按需，约 1 天，必须独审）

按第 3 节清单逐项扩展 G3 解析。每一项都配对两类测试：正向（能正确识别）和反向（攻击样本仍被拒）。对“负数、零、非法日期”这类被拒原因，给出具体的固定追问文案。只扩展识别能力，不放宽任何授权规则。

### 阶段 D：live 验证
