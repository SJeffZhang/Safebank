# 架构与执行流程

SafeBank 把业务规划、授权决策和银行执行分开。L1 可以提出操作计划；L2 判断计划是否在用户授权范围内、是否满足金融规则；L3 负责把获准的业务原子地写入数据库。

## 部署边界

| 组件 | 所在网络 | 持有的主要能力 |
|---|---|---|
| App / BFF | `agent-net` | 客户登录与同站会话；直接提交原话、表单、审批与 OTP |
| L1 Agent | `agent-net` | 读取与当前原话绑定的助手令牌，调用 L2；保存 LangGraph 检查点 |
| L2 Gateway | `agent-net` + `bank-net` | 独立验证来源、签发审批、访问 L3；保存授权、执行状态与审计 |
| L3 Backend | `bank-net` | 校验服务凭证与执行信封，运行金融规则并持久化 |
| PostgreSQL | 各自网络 | 银行与网关分库分角色，助手检查点使用另一实例 |

Compose 只向宿主发布 BFF 的 `127.0.0.1:3000`。网关公共接口监听 `agent-net:8200`，内部调度回调监听 `bank-net:8201`；两者路由集合分离。L1 没有银行网络接口，也没有 L3 调用令牌。

浏览器通过 HttpOnly、SameSite cookie 维护会话。服务令牌与 app / assistant JWT 留在服务端；BFF 对写请求检查 Origin 和自定义请求头。审批与 OTP 请求从 BFF 直接进入 L2。

部署定义见 [`docker-compose.yml`](../docker-compose.yml)，授权矩阵见 [`auth/matrix.py`](../services/gateway/app/auth/matrix.py)。

## 一份计划如何被执行

1. **登记原话。** BFF 把用户输入交给 L2，保存原话、作用域与有效期，再把绑定该输入的助手令牌交给 L1。引用、提示采纳、页面上下文和手工键入的授权含义分别处理。
2. **理解与收集。** L1 通过 LangGraph 理解任务，只绑定读工具补充账户、卡、收款人和产品等信息。缺少关键条件时追问。
3. **生成计划。** 模型返回结构化步骤和参数来源；客户、会话、请求等身份字段由代码填写。共享契约先做类型与形状校验。
4. **评估。** L2 按下面的九阶段流水线运行，生成决策、风险理由和预演结果。
5. **确认。** 需要审批时，L1 在检查点暂停。App 按 `approval_id` 读取 L2 的确认面板，用户核对后提交 `view_hash`；红级同时验证 OTP。
6. **复演与执行。** 恢复后的执行请求重新核验有效期、撤销状态和快照。需要时重新审批，满足条件后才调用 L3。
7. **核验结果。** L3 事务内提交账本、业务状态、执行记录和 outbox。L1 校验输出后回复，界面按权威执行结果更新。

表单走同一评估与执行路径。L2 从持久化的 `form_action_id` 重建步骤，检查用户、会话、期限、字段与授权代际；客户端不能直接提交一组任意步骤冒充表单。详见[表单授权验收](acceptance/form-authorization.md)。

## 网关九阶段流水线

| 阶段 | 作用 |
|---|---|
| 契约 | 工具白名单、参数形状与调用来源 |
| 实体 | 账户、卡片、收款人和产品存在性、归属及引用 |
| 来源与污点 | 参数对应的原话、读结果、表单或可重算派生值 |
| 意图 | 目标与金额是否在用户授权范围内 |
| 快照 | 固定客户版本与模拟时钟版本 |
| 预演 | 在影子状态上累积执行计划，检查金融约束及七天预留 |
| 工作流 | 当前与历史操作中的累计转出、拆分与危险组合 |
| 决策 | 汇总为 `ALLOW`、`REQUIRE_APPROVAL`、`REPLAN` 或 `DENY` |
| 审计 | 保存决策依据与哈希链事件 |

实现见 [`pipeline/`](../services/gateway/app/pipeline/)，工具策略见 [`tools.yaml`](../services/gateway/policies/tools.yaml)。预演只修改内存状态；授权与审计写入网关库，不写银行业务库。

## 金融一致性与恢复

[`bankcore`](../packages/bankcore/) 不访问数据库、网络或系统时钟。调用方传入 `BankState`、时间和计划步骤，取得新状态、类型化效果与违规结果。L2 使用它预演，L3 使用它生成真实写入效果。

金额用整数分，份额用四位 `Decimal`。账本区分已过账与在途量；写事务使用锁、客户版本和时钟版本约束并发。多步骤计划出现硬约束失败时，不保留前面步骤的部分业务效果。

执行采用 `prepare / execute / reconcile`：同一客户与计划使用稳定身份；超时不推断失败，也不创建新计划重试。`UNKNOWN` 通过对账恢复，已取消的执行意图永久阻断迟到请求。状态变化导致的新尝试有独立 attempt 和证据历史。

相关设计见 [ADR-007](decisions/ADR-007-execution-identity-outbox.md)、[ADR-008](decisions/ADR-008-state-changed-fence.md)。

## 定时、代扣与基金事件

模拟时钟将定时转账、商户账单、基金确认和结算放到可复现的时间轴上。L3 调度器发现到期事件后，通过内部接口请求 L2；L2 核实授权条款与当前状态后主动执行或拦截。事件身份包含来源与到期时刻，终态不能重复执行。

固定种子中的既有代扣与定时指令，需要由本地维护 CLI 在空网关库中安装合成的既有授权。它只接受与固定种子完全匹配的条款，不伪造用户审批或模型执行记录。普通新建定时业务的授权来自真实获批并已执行的来源计划。

代码见 [`internal/scheduled.py`](../services/gateway/app/internal/scheduled.py)、[`scheduler.py`](../services/bank-backend/app/scheduler.py)，事件身份约定见 [ADR-012](decisions/ADR-012-demo-event-identity.md)。

## 设计边界

本项目验证银行智能体的执行安全，不连接真实支付、清算或短信通道。黄级审批依赖浏览器完整性；演示验证码不能替代生产环境的带外认证。会话持久化、多实例、高可用和生产容量不属于本轮验收。详细范围见 [SECURITY.md](../SECURITY.md) 与 [验证说明](validation.md)。
